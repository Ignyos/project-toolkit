# dotnet-windows-desktop — Implementation Steps

Follow these step-by-step instructions to generate or reconcile a `dotnet-windows-desktop` workflow implementation for a target project.

## 0. Determine Greenfield vs. Existing Project Context

Before generating any files, inspect the target project directory:

### Greenfield Project (New Project)
1. Initialize the solution and project structure if not already present.
2. Designate the primary desktop host project file (e.g., `*.Host.csproj` or main executable project) as the single `<Version>` source of truth.
3. Create `AGENTS.md` and `.github/copilot-instructions.md` fresh, seeded with the direction rules from `architecture.md` and `requirements.md`.
4. Create the `PM/` folder structure per `shared/project-management/workflow.md`.

### Existing Project (Refactoring / Adoption)
1. Read all existing `.csproj` files across the solution.
2. Identify or establish the single primary project file that will hold the canonical `<Version>`. Ensure other `.csproj` files do not maintain independent competing version tags.
3. Read existing `AGENTS.md` or `.github/copilot-instructions.md` files. **Do not overwrite existing status or project-specific rules.** Reconcile and append the profile's direction rules and PM pointer sentence without clobbering existing project context.
4. Verify whether a `dev` branch exists alongside `main`. If only `main` exists, establish a `dev` branch to satisfy the Dual-Lane By Default requirement.
5. Reconcile or create the `PM/` folder structure, preserving any existing roadmap or task items by migrating them into the appropriate `PM/` lifecycle folders.

## 1. Apply Origin Breadcrumb

On every script or workflow file generated by this profile, add the comment header defined in `shared/breadcrumb-spec.md` as the first lines of the file.

## 2. Generate Release and Publish Scripts

Using the files in `reference/` as a stylistic reference (not a verbatim template):

1. Generate `scripts/release-common.ps1` with helper functions tailored to this project's paths, git commands, semver parsing, and dev version suggestion logic.
2. Generate `scripts/publish-live.ps1` enforcing `main` branch execution, clean working tree check, version bump validation (fourth node must be `.0`), diff generation, AI release notes prompt & confirmation loop, tag creation, and push.
3. Generate `scripts/publish-dev.ps1` enforcing `dev` branch execution, non-zero fourth-node version suggestion, skipping release notes requirement, and dev branch commit/push.
4. Generate `scripts/validate-publish-parity.ps1` containing parity checks specific to the generated scripts to ensure branch gates and functions remain intact.
5. If installer packaging is required, generate `scripts/build-dev-installer.ps1` and the corresponding Inno Setup script (`installer/*.iss`), ensuring application logo icons and wizard artwork are properly referenced.

## 3. Generate VS Code Launch Configurations & GitHub Workflows

1. **`.vscode/launch.json` Handling**:
   - **Greenfield**: Generate `.vscode/launch.json` fresh using `reference/.vscode/launch.json` as a guide.
   - **Existing**: Read the existing `.vscode/launch.json`. Merge standard Run & Debug tasks (`Build`, `Publish-dev`, `Publish-live`, and host process execution) without removing or clobbering existing custom debug configurations.
2. **`.github/workflows/` Handling**:
   - **Greenfield**: Create `.github/workflows/publish-dev.yml` and `.github/workflows/release-artifacts.yml` tailored to the target repository.
   - **Existing**: Reconcile existing workflows. Preserve existing workflow steps while ensuring build, checksum, and manifest triggers match the profile requirements.

## 4. Set Up Project Management Structure

Generate the `PM/` lifecycle directories:
- `PM/project-management.md` (pure index)
- `PM/workflow.md` (checkpoint and lifecycle rules)
- `PM/backlog/`, `PM/current/`, `PM/release-candidate-dev/`, `PM/release-candidate/`, `PM/completed/`

## 5. Execute Acceptance Verification

Walk through `acceptance-checklist.md` to verify that every requirement in `requirements.md` has been satisfied by the generated implementation.
