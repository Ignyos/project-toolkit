# vanilla-js-github-pages-spa — Implementation Steps

Follow these step-by-step instructions to generate or reconcile a `vanilla-js-github-pages-spa` workflow implementation for a target project.

## 0. Determine Greenfield vs. Existing Project Context

Before generating any files, inspect the target project directory:

### Greenfield Project (New Project)
1. Initialize the HTML/JS application structure inside `docs/` (or repository root if `docs/` is not used).
2. Create `docs/CNAME` with the target production domain (e.g. `app.ignyos.com`).
3. Create `AGENTS.md` and `.github/copilot-instructions.md` fresh, seeded with direction rules from `architecture.md` and `requirements.md`.
4. Create the `PM/` folder structure per `shared/project-management/workflow.md`.

### Existing Project (Refactoring / Adoption)
1. Inspect the existing static file structure. If static assets live in `docs/` or root, preserve that layout.
2. Read existing `AGENTS.md` or `.github/copilot-instructions.md` files. **Do not overwrite existing status or project-specific rules.** Reconcile and append profile direction rules and the PM pointer sentence without clobbering existing project context.
3. Verify whether a `dev` branch exists alongside `main`. If only `main` exists, establish a `dev` branch to satisfy the Dual-Lane By Default requirement.
4. Verify CNAME configurations for both production and dev repos/subdomains.
5. Reconcile or create the `PM/` folder structure, preserving existing roadmap or task items by migrating them into the appropriate `PM/` lifecycle folders.

## 1. Apply Origin Breadcrumb

On every script, workflow, or markdown file generated by this profile, add the comment header defined in `shared/breadcrumb-spec.md` as the first lines of the file.

## 2. Generate Validation and Clean Scripts

1. Generate `build.ps1` to validate that the deployment source directory (`docs/`) exists and contains required entry points (`index.html`).
2. Generate `clean.ps1` to safely clean deployment output directories if applicable.

## 3. Generate Dev Publish Script

Using `reference/dev-publish.ps1` as a stylistic reference:
1. Enforce execution on `dev` branch only.
2. Generate UTC timestamp (`yyyy-MM-dd-HH-mm`).
3. Update asset version parameters (`?v=<timestamp>`) in `index.html` files.
4. Update `CACHE_NAME` in `docs/service-worker.js`.
5. Perform `git add`, `git commit`, and `git push origin dev`.

## 4. Generate Production Release Script & Release Notes Style Guide

Using `reference/release.ps1` and `reference/RELEASE_NOTES_STYLE.md` as reference:
1. Enforce execution on `main` branch only (run test-mode dry run on non-main branches).
2. Check for clean working tree.
3. Generate UTC timestamp and git tag name `<timestamp>`.
4. Update asset query strings and service worker cache name.
5. Generate release diff and save to `release/rel-<timestamp>.txt`.
6. Emit/copy AI prompt for `RELEASE_NOTES.md` generation based on diff evidence and `RELEASE_NOTES_STYLE.md`.
7. Pause for human/AI interactive release notes update confirmation.
8. Commit release diff and notes, create annotated tag `<timestamp>`, and push branch and tag to origin.

## 5. Generate GitHub Actions Workflows

Using `reference/.github/workflows/` as reference:
1. **Greenfield**:
   - Generate `.github/workflows/deploy-dev-pages.yml` triggering on push to `dev` to force-push `./docs` to the external dev repository using `DEV_PAGES_TOKEN` and `DEV_PAGES_REPO` secrets.
   - Generate `.github/workflows/release.yml` triggering on tag push (`*`) to create a GitHub Release with `RELEASE_NOTES.md` as body.
2. **Existing**:
   - Reconcile existing workflows. Preserve existing workflow steps while verifying secrets and deployment targets match the project's CNAME configuration.

## 6. Configure Environment Safety Banner & CNAMEs

1. Add `docs/dev-site-banner.js` and include banner initialization snippet in `docs/index.html`.
2. Configure production `docs/CNAME`.

## 7. Generate VS Code Launch Configurations

1. **Greenfield**: Generate `.vscode/launch.json` fresh using `reference/.vscode/launch.json` as a guide (`Build`, `Publish-dev`, `Publish-live`).
2. **Existing**: Read existing `.vscode/launch.json` and merge the standard Run & Debug tasks without overwriting existing custom debug tasks.

## 8. Set Up Project Management Structure

Generate `PM/` lifecycle directories:
- `PM/project-management.md` (pure index)
- `PM/workflow.md` (checkpoint and lifecycle rules)
- `PM/backlog/`, `PM/current/`, `PM/release-candidate-dev/`, `PM/release-candidate/`, `PM/completed/`

## 9. Execute Acceptance Verification

Walk through `acceptance-checklist.md` to verify that every requirement in `requirements.md` has been satisfied by the generated implementation.
